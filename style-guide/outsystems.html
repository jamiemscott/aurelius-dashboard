Style Guide

OutSystems Integration

Aurelius runs inside OutSystems, which injects markup and CSS that we cannot modify. This page documents every known OS behaviour that conflicts with our design system, the root cause of each, and the override pattern used to fix it. All override CSS lives in src/styles/theme/osui-bridge.css (token mappings and structural fixes) or within the relevant component module.

The Core Problem: @layer

Before looking at individual fixes, it helps to understand why OS overrides are tricky in the first place.

Problem

OS wraps our entire bundle.css inside @layer theme.theme at runtime. OS's own _Basic_ stylesheet is unlayered. In the normal cascade, unlayered CSS beats all layered CSS regardless of specificity.

Solution

!important reverses the layer order. A !important declaration inside a layer beats a regular unlayered declaration. Use it only on properties where _Basic_ is known to set a competing value.

Cascade priority — normal declarations (low → high)

Our layered CSS
@layer theme.theme
→
OS _Basic_ CSS
unlayered — wins

Cascade priority — !important declarations (reversed)

OS _Basic_ !important
unlayered — loses
→
Our layered !important
wins
/* Normal rule — OS _Basic_ (unlayered) will beat this */
.my-element { border-radius: 12px; }

/* !important rule — beats OS _Basic_'s regular declarations */
.my-element { border-radius: 12px !important; }

/* Rule of thumb: only use !important when _Basic_ is known
   to set the same property. Keep the surface area minimal. */

Token Bridge

OS components reference their own CSS custom property vocabulary (--color-primary, --font-size-base, etc.). The token bridge in src/styles/theme/osui-bridge.css maps every OSUI variable to the nearest Aurelius token so OS components automatically adopt the Aurelius visual language without touching OS source files. The bridge is a one-way adapter — only OSUI variables are declared here, Aurelius tokens are never modified.

Pattern: display: contents

OS frequently wraps elements in extra <div> or <span> containers that it cannot be told to remove. When these wrappers become flex or grid children they disrupt layout — they consume space and the intended child element is no longer a direct participant in the parent's layout context. display: contents removes the wrapper from the layout tree entirely while leaving its children in place, as if the wrapper element never existed.

Location OS wrapper Problem Fix
Topbar — inline SVG icons [data-block*="InlineSVG"], .osui-inline-svg Two wrapper divs become flex children instead of the SVG; height: 100% inline style on inner div causes misalignment display: contents on both wrappers — SVG participates in flex directly
Topbar — theme toggle [data-block*="ThemeSwitcher"], .theme-switcher > span Outer OSBlockWidget consumes full flex width; inner <span> wraps the checkbox and also becomes a flex child display: contents !important on both (needs !important — see @layer section)
Footer .site-footer .OSBlockWidget Three footer children wrapped in one OSBlockWidget, collapsing the three-column flex row into one child display: contents — all three children reach .footer-bottom's flex directly
Adviser input bar .adv-input-bar > span OS wraps the <textarea> in a <span> — the span becomes the flex child and the textarea loses its flex: 1 growth display: contents — textarea behaves as a direct flex child again 
/* Removes the OS wrapper from the layout tree.
   Children participate in the parent flex/grid directly. */
.adv-input-bar > span {
  display: contents;
}

/* Use !important when the wrapper also carries an OS class
   that _Basic_ styles with display:block */
[data-block*="ThemeSwitcher"],
.theme-switcher > span {
  display: contents !important;
}

Pattern: ThemeGrid Suppression

OutSystems automatically adds ThemeGrid_* utility classes to block-level elements. These classes add unwanted margins and padding that pollute custom layouts. A single global rule suppresses them all.

/* src/styles/theme/osui-bridge.css */

/* ThemeGrid is not used — suppress all injected utility classes globally */
[class*="ThemeGrid_"] {
  margin: 0;
  padding: 0;
}

OS injects classes like ThemeGrid_MarginGutter, ThemeGrid_Row, and similar siblings on block elements throughout the page. Without this reset they add inconsistent horizontal margins that interfere with the topbar pill, sidebar, and card layouts.

Pattern: Dropdown Arrow

OS wraps every <select> in a <div class="dropdown-container"> and renders a chevron arrow via a ::after pseudo-element on that wrapper. Our <select> already has its own SVG arrow baked into the background-image, so the OS arrow creates a double-arrow. The fix is two rules: make the wrapper fill available space, and suppress the pseudo-element arrow.

Root cause Fix
.dropdown-container has no width — it doesn't stretch to fill the parent flex column, so the <select> inside it collapses flex: 1; min-width: 0 on .chat-context-field .dropdown-container
.dropdown-container::after renders an icon-font arrow via content: var(--osui-icon-arrow-down) content: none !important — cleaner than display: none for pseudo-elements; doesn't disturb the box model or OS transition styles
Future OS widget versions may change the arrow pattern (sibling element instead of pseudo-element) Fallback rule hides any sibling <svg>, <i>, or element with arrow/chevron/caret in its class name 
/* src/styles/modules/adviser.css */

/* 1. Make wrapper fill available space */
.chat-context-field .dropdown-container {
  flex: 1;
  min-width: 0;
  position: relative; /* preserve stacking context for OS transitions */
}

/* 2. Kill the icon-font arrow pseudo-element */
.chat-context-field .dropdown-container::after {
  content: none !important;
}

/* 3. Fallback for any sibling arrow nodes OS may inject */
.chat-context-field select ~ svg,
.chat-context-field select ~ i,
.chat-context-field select ~ span[class],
.chat-context-field [class*="arrow"],
.chat-context-field [class*="chevron"],
.chat-context-field [class*="caret"] {
  display: none !important;
}

Pattern: OSFillParent

OS adds the OSFillParent class to elements it wants to stretch full-width. The class is defined in _Basic_ as unlayered CSS: .OSFillParent { display: block; width: 100%; }. This is exactly the scenario where the @layer problem bites hardest — specificity is equal (one class each), but _Basic_ is unlayered so it wins. The !important fix is unavoidable here.

/* _Basic_ (unlayered, wins by default):
   .OSFillParent { display: block; width: 100%; }

   Our fix — in @layer theme.theme (would normally lose):
   !important reverses the priority so we win */
.theme-toggle.OSFillParent {
  display: flex  !important;
  flex: 0 0 auto !important;
  width: auto    !important;
}

Adding a New Override

When a new OS conflict surfaces, follow this decision tree to choose the right approach and the right file.

1
Is it a token mapping? (OS variable → Aurelius value)
→ Add to :root in osui-bridge.css. No !important needed.
2
Is it a global structural fix? (ThemeGrid, InlineSVG, ThemeSwitcher, Footer)
→ Add to osui-bridge.css below the token block. May need !important.
3
Is it scoped to a specific component? (adviser chat selects, feedback messages)
→ Add to the component's module file (e.g. modules/adviser.css, modules/feedback.css) in a clearly labelled OS compat block.
4
Does it need !important?
Only if _Basic_ sets the same property. Use DevTools to confirm: if OS is winning and our rule is being overridden, !important is the fix. Document why in a comment.
/* Template for a new component-scoped OS override block */

/* ─── OUTSYSTEMS COMPAT ──────────────────────────────────────
 * [Describe what OS injects and why it conflicts]
 *
 * OS markup:
 *   <div class="os-wrapper">
 *     <our-element>…</our-element>
 *   </div>
 */
.our-scope .os-wrapper {
  display: contents; /* remove from layout tree */
}

/* needs !important: _Basic_ sets display:block on this class */
.our-scope .OSFillParent {
  width: auto !important;
}
